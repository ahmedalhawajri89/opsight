# Opsight — Product Definition & MVP Scope

Phase 00 document. Nothing here is implemented yet.

---

## 1. The problem

A small or mid-sized operating business records its activity in fragments: orders in
one place, stock counts in another, expenses in a spreadsheet, customer history in
someone's head. Each fragment is individually accurate and collectively useless. The
owner can answer "what did we sell yesterday?" but not "is our margin eroding, and
which products are causing it?"

The gap is not data collection. It is the absence of a **defined, trustworthy
calculation layer** on top of the data, and a way to see change over time.

## 2. What Opsight is

Opsight is an internal operations system for one business. It is the system of record
for operational transactions **and** the analysis layer over them.

It does four things, in strict order of dependency:

1. **Records** operational facts (orders, stock movements, expenses).
2. **Calculates** defined metrics from those facts.
3. **Compares** metrics across periods and segments.
4. **Surfaces** observations worth acting on.

## 3. What Opsight is not

- Not an accounting or tax system. It reports operational profit, not statutory accounts.
- Not a POS or storefront. It records orders; it does not take payments.
- Not a data warehouse or ETL tool. There are no external connectors in the MVP.
- Not a multi-tenant SaaS in the MVP (see [DECISIONS.md](../architecture/DECISIONS.md), ADR-001).
- Not an AI/ML product. Insights are deterministic rules, not predictions.

## 4. The four data layers

These layers must never be conflated. Every feature belongs to exactly one.

### L0 — Source data

Raw business records, entered by humans or an integration. **The only writable layer.**

Tables: `customers`, `products`, `categories`, `orders`, `order_items`,
`inventory_items`, `inventory_movements`, `expenses`, `expense_categories`, `users`,
`activity_logs`, `business_settings`.

Properties:

- Every row is a statement of fact about something that happened.
- Rows describing a past event are **immutable once finalized** (see §5).
- Money and cost values on transactional rows are **snapshots**, not references.

### L1 — Metrics

Pure functions over L0 for a period. Defined once, in one place, in the backend.

Examples: Net Revenue, COGS, Gross Margin, AOV, Cancellation Rate.

Properties:

- **Never stored** as authoritative values. Always derived at query time.
- A metric has exactly one definition project-wide. The API, a report and a chart must
  never compute the same metric two different ways.
- Deterministic: same inputs, same period, same timezone produce the same output, forever.
- A rollup table may exist later purely as a **rebuildable cache** (ADR-009).

### L2 — Analytics

Metrics arranged over a dimension: time series, period-over-period comparison,
breakdown by category/product/customer, ranking.

Properties:

- Composed from L1. Never reads L0 with its own ad-hoc arithmetic.
- Always carries the period, comparison basis and timezone in its response.

### L3 — Insights

Observations generated by explicit rules over L2 output.

Example: *"Gross margin fell 4.2 pp vs the previous 30 days; COGS rose 18% while
revenue rose 6%."*

Properties:

- Rule-based and deterministic. Each rule has an id, a severity, the metrics it reads,
  a threshold and a message template.
- Every insight must link back to the analytics view that produced it.
- No statistical modelling in the MVP. Anomaly detection is post-MVP (ADR-010).

**Layer rule:** L1 reads only L0. L2 reads only L1. L3 reads only L2. A violation of
this is a defect, not a shortcut.

## 5. Immutability and historical truth

The single most important correctness rule in Opsight:

> **A change to a catalog record must never change a past metric.**

If a product's selling price rises from 20 to 25 today, last month's revenue must not
move. Therefore:

- `order_items` stores `product_name`, `sku`, `unit_price` and `unit_cost` **copied at
  the moment the order is confirmed**. It joins to `products` for navigation only,
  never for money.
- Finalized orders (`confirmed`, `fulfilled`, `cancelled`, `refunded`) are not editable.
  Corrections happen by cancelling and re-entering, which leaves both facts on record.
- `inventory_movements` is an append-only ledger. Stock is never "set"; it is moved.
- `activity_logs` is append-only. No updates, no deletes, ever.

## 6. MVP modules

Status key: **MVP** = in the first shippable version. **Post-MVP** = designed for, built later.

---

### 6.1 Authentication — MVP

**Purpose.** Establish who is using the system, for both access control and audit attribution.

**Core entities.** `users`, Sanctum session state.

**Operations.** Log in, log out, fetch current user and abilities, change own password.

**Business rules.**

- Self-registration is disabled. Users are created by an Owner (§6.10).
- A deactivated user (`is_active = false`) cannot authenticate, and an existing session
  is rejected on its next request.
- Failed logins are rate limited per IP and email (see SECURITY.md).
- Password reset by email is **Post-MVP**. The MVP allows an Owner to set a temporary password.

**Dependencies.** None. Everything else depends on it.

---

### 6.2 Dashboard — MVP

**Purpose.** The daily answer to "how is the business doing, and what changed?"

**Core entities.** None of its own. It is a composition of L1 and L2 output.

**Operations.** View a KPI summary for a selected period with comparison; view revenue
and order trend; view top products and top customers; view low-stock alerts; view insights.

**Business rules.**

- Every figure carries its period and comparison basis explicitly on screen.
- A period that includes today is labelled **incomplete** and excluded from trend conclusions.
- Cost, COGS, margin and profit tiles are withheld **server-side** from roles without
  `metrics.view_cost` (see ROLES_AND_PERMISSIONS.md).
- The dashboard issues no writes.

**Dependencies.** Orders, Products, Customers, Inventory, Expenses, Analytics.

---

### 6.3 Orders — MVP

**Purpose.** The primary revenue-bearing record. Source of revenue, COGS, AOV and
cancellation metrics, and the trigger for outbound stock movement.

**Core entities.** `orders`, `order_items`.

**Operations.** List with filters, view detail, create draft, add and remove line items
while draft, confirm, mark fulfilled, cancel, record refund.

**Business rules.**

- Status lifecycle is a strict state machine:
  `draft → confirmed → fulfilled`, plus `draft|confirmed|fulfilled → cancelled` and
  `fulfilled → refunded`. No other transition is permitted.
- `draft` orders are **excluded from every metric**. They are working documents.
- **Confirming** an order is the commitment point. At that instant, inside one database
  transaction: price and cost are snapshotted onto each line, stock is decremented via
  `inventory_movements`, and `placed_at` is set.
- An order cannot be confirmed with zero line items.
- An order cannot be confirmed if any line exceeds available stock (ADR-007 records the
  backorder alternative).
- **Cancelling** a confirmed or fulfilled order writes a compensating inventory movement
  returning the stock. It does not delete the order.
- Line totals are computed server-side from `unit_price × quantity`. Client-supplied
  totals are ignored.
- `placed_at`, not `created_at`, is the business date used by every metric.
- Orders are never hard-deleted.

**Dependencies.** Customers, Products, Inventory.

---

### 6.4 Customers — MVP

**Purpose.** Attribute orders to a buyer so that growth, retention and concentration
can be measured.

**Core entities.** `customers`.

**Operations.** List, search, view detail with order history and lifetime value, create,
edit, deactivate.

**Business rules.**

- `email` is unique when present, and may be absent (walk-in trade).
- A customer with at least one non-draft order cannot be hard-deleted; only soft-deleted.
- Soft-deleted customers remain in historical metrics. Removing a customer must not
  rewrite history.
- "New customer" is **derived** from the date of their first qualifying order, never
  stored on the row (see METRICS.md).
- Lifetime value is a metric (L1), not a column.

**Dependencies.** Orders, for history and derived fields.

---

### 6.5 Products — MVP

**Purpose.** The catalog. Supplies current price and cost at the moment of sale, and
the dimension for product-level analytics.

**Core entities.** `products`, `categories`.

**Operations.** List with filters, view detail with sales history, create, edit,
activate and deactivate.

**Business rules.**

- `sku` is unique and immutable after creation.
- Editing `price` or `cost` affects **future** orders only. Past `order_items` are untouched.
- A product with sales history cannot be hard-deleted; deactivate instead.
- Deactivated products cannot be added to new orders but remain fully visible in analytics.
- `cost` is restricted: roles without `products.view_cost` never receive the field.
- Categories are a **flat, single level** in the MVP. Hierarchy is deliberately excluded (ADR-008).

**Dependencies.** Categories. Inventory depends on Products.

---

### 6.6 Inventory — MVP

**Purpose.** Know what is physically on hand, why it changed, and what is about to run out.

**Core entities.** `inventory_items` (current state), `inventory_movements` (the ledger).

**Operations.** View stock levels, view a product's movement history, record a manual
adjustment with a reason, record a purchase or restock, view the low-stock list.

**Business rules.**

- `inventory_movements` is the **source of truth** and is append-only. Every row records
  a signed `quantity_delta`, a `reason`, and a polymorphic reference to what caused it.
- `inventory_items.stock_on_hand` is a **derived cache** maintained inside the same
  transaction as the movement that changed it, under a row lock.
- **Invariant:** `inventory_items.stock_on_hand == SUM(inventory_movements.quantity_delta)`
  for every product, at all times. This is asserted by an automated test and by a
  reconciliation command.
- Stock may not go negative through a sale. A manual adjustment to a negative value is
  rejected; a correction is entered as a delta.
- Every manual adjustment requires a non-empty reason and is written to `activity_logs`.
- Single stock location in the MVP. Multi-warehouse is Post-MVP (ADR-006).

**Dependencies.** Products. Orders write to it.

---

### 6.7 Expenses — MVP

**Purpose.** Supply the cost side of operating profit, so the dashboard reports profit
rather than revenue alone.

**Core entities.** `expenses`, `expense_categories`.

**Operations.** List with filters, create, edit, delete, view breakdown by category.

**Business rules.**

- `incurred_on` is a **date**, not a timestamp, and is the business date for expense
  metrics. It may differ from the entry date and may be backdated.
- Recurring expenses are entered as individual rows in the MVP. Recurrence automation is Post-MVP.
- Expenses are operating expenses only. Cost of goods reaches profit through COGS from
  `order_items`, never as an expense row. **Entering stock purchases as expenses would
  double-count them** — the UI must state this, and the restock flow must not create one.
- Only roles with `expenses.view` may see this module at all. It is the primary financial
  boundary between Staff and Manager.

**Dependencies.** None for writing. Feeds Analytics.

---

### 6.8 Analytics — MVP (core) / Post-MVP (depth)

**Purpose.** Turn metrics into comparison and explanation.

**Core entities.** None. Read-only over L1.

**MVP scope.**

- Period selector with presets: 7d, 30d, 90d, MTD, QTD, YTD, custom.
- Comparison against the immediately preceding period of equal length, or the same
  period one year earlier.
- Revenue, orders and profit time series at daily or monthly grain.
- Breakdown by product, category and customer.
- Top-N rankings with each row's contribution share.

**Post-MVP.** Cohort retention, RFM segmentation, forecasting, saved views.

**Business rules.**

- Every response states `from`, `to`, `timezone`, `comparison_basis` and `is_partial`.
- Comparing an incomplete current period against a complete prior period must be flagged
  in the payload so the UI can warn.
- Percentage change against a zero or negative base is returned as `null`, never as `0`,
  infinity, or a fabricated number.

**Dependencies.** All source modules.

---

### 6.9 Reports — Post-MVP (CSV export is MVP)

**Purpose.** Take analysis out of the system for sharing and archiving.

**MVP scope.** Synchronous CSV export of any table view, respecting the caller's current
filters **and** their field-level permissions.

**Post-MVP.** Saved report definitions, queued PDF generation, scheduled email delivery,
report history.

**Business rules.**

- An export contains exactly the rows and columns the requesting user is authorized to
  see. Export is never a permission bypass.
- Every export is written to `activity_logs` with the filters used.
- Exports are rate limited (SECURITY.md).

**Dependencies.** Analytics, Authorization.

---

### 6.10 Users & Roles — MVP

**Purpose.** Control who may do what, and make audit attribution meaningful.

**Core entities.** `users`, carrying a `role` column.

**Operations.** List users, create a user with a role, change a user's role, deactivate
and reactivate, reset a user's password.

**Business rules.**

- Only an Owner may manage users.
- A user cannot change their own role, deactivate themselves, or delete themselves.
- The system must always retain **at least one active Owner**. The last one cannot be
  demoted or deactivated.
- Roles are a fixed, code-defined set in the MVP. Custom roles are Post-MVP (ADR-003).
- Users are deactivated, never deleted, so that historical `activity_logs` and
  `created_by` references stay resolvable.

**Dependencies.** Authentication.

---

### 6.11 Activity Log — MVP

**Purpose.** Answer "who changed this, when, and what did it look like before?"

**Core entities.** `activity_logs`.

**Operations.** List with filters by actor, action, subject and date range; view the
entries for a specific record.

**Business rules.**

- Append-only. The application exposes no update or delete path for it.
- Logged: every create, update and delete of source data; every order status transition;
  every inventory adjustment; every auth event; every export; every user or role change.
- Not logged: read traffic on ordinary list and detail endpoints — volume without value.
- Each entry records actor, action, subject type and id, a before/after diff of changed
  attributes only, IP and user agent.
- Passwords, tokens and session identifiers are **never** written to the log.
- Visible to Owner and Manager only.

**Dependencies.** All modules write to it.

## 7. MVP summary

| Module | Status | Rationale |
| --- | --- | --- |
| Authentication | MVP | Prerequisite for everything |
| Users & Roles | MVP | Authorization boundaries are a core requirement |
| Customers | MVP | Order dimension |
| Products & Categories | MVP | Order dimension, source of price and cost |
| Orders | MVP | The revenue-bearing record; without it there is no BI |
| Inventory | MVP | Operational visibility is half the product |
| Expenses | MVP | Without it Opsight reports revenue, not profit |
| Analytics | MVP (core) | The reason the product exists |
| Dashboard | MVP | The primary surface |
| Activity Log | MVP | Trust and auditability |
| Reports | CSV only | Full reporting defers cleanly without weakening the MVP |

**Explicitly out of the MVP:** multi-tenancy, multi-warehouse, category hierarchy,
purchase orders and suppliers, partial or multiple refunds, custom roles, localization,
scheduled email reports, PDF export, notifications, anomaly detection, forecasting,
external integrations, mobile app.

## 8. Definition of done for the MVP

1. A user logs in and lands on a dashboard populated from real records.
2. Each of the four roles sees exactly what ROLES_AND_PERMISSIONS.md specifies, enforced
   server-side.
3. Orders can be created, confirmed, fulfilled, cancelled and refunded, and stock moves
   correctly and reversibly at each step.
4. Every metric in METRICS.md returns a value matching a hand-calculated figure against a
   known seeded dataset.
5. Editing a product's price or cost provably does not change any historical metric.
6. The inventory ledger invariant holds under a concurrent-order test.
7. Every business rule marked **must** in these documents has a passing automated test.
